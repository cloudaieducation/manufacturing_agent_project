tests/evaluate_mcp_server02_rag에 교육용 주석을 최대한 촘촘하게 추가해줘.

작업 대상:

* tests/evaluate_mcp_server02_rag가 단일 파일이면 해당 파일만 수정한다.
* tests/evaluate_mcp_server02_rag가 폴더이면 폴더 내부의 테스트 파일만 대상으로 한다.
* 관련 없는 파일은 수정하지 않는다.

작업 목표:

* 코드 동작은 절대 변경하지 않고, 주석과 docstring만 보강한다.
* 테스트 코드의 실행 흐름, 테스트 목적, 입력값, 기대 결과, 실패 시 의미를 교육용으로 이해하기 쉽게 설명한다.
* 교육생이 “왜 이 테스트가 필요한지”, “무엇을 검증하는지”, “어떤 순서로 실행되는지” 이해할 수 있도록 작성한다.
* 주석은 “무엇을 하는 코드인지”뿐 아니라 “왜 필요한 코드인지”까지 설명한다.
* 단, 변수명이나 함수명만 읽어도 바로 알 수 있는 단순 설명은 피한다.

중요 제한사항:

* 함수명, 변수명, 클래스명, import, 로직, 조건문, 반환값, assert 조건은 변경하지 않는다.
* 테스트 결과가 바뀌면 안 된다.
* timeout 값, transport 방식, 서버 실행 방식, fixture 구조를 변경하지 않는다.
* print, logging 출력 문구는 변경하지 않는다.
* 이미 있는 주석은 삭제하지 말고, 필요하면 더 명확하게 보강한다.
* 보안상 민감한 값, 환경변수 값, API Key, 토큰 등을 주석에 예시로 노출하지 않는다.
* 수정이 필요해 보이는 로직 문제가 있어도 직접 고치지 말고, 별도 검토 의견으로만 보고한다.

주석 추가 기준:

1. 파일 상단 주석

   * 이 테스트 파일의 목적을 설명한다.
   * mcp_server02의 RAG 기능 중 무엇을 검증하는지 설명한다.
   * 테스트 대상이 서버 실행, MCP Tool 호출, RAG 검색 결과, timeout, 실패 처리 중 어디에 해당하는지 요약한다.

2. import 구문

   * 모든 import 줄마다 주석을 달지 않는다.
   * 표준 라이브러리 / 외부 라이브러리 / 프로젝트 내부 모듈 단위로 묶어서 역할을 설명한다.
   * import 자체의 순서나 구조는 변경하지 않는다.

3. 상수와 설정값

   * 경로, timeout, 테스트 질문, 기대값, 환경변수 관련 상수가 있다면 각각의 의미를 설명한다.
   * timeout 값이 있다면 “무한 대기 방지”, “RAG 응답 지연 탐지”, “서버 hang 조기 발견” 관점에서 설명한다.
   * 단, timeout 값을 변경하지 않는다.

4. fixture

   * pytest fixture가 있다면 언제 생성되고 언제 정리되는지 설명한다.
   * 서버 프로세스, 클라이언트, 임시 파일, 환경변수 설정 fixture가 있다면 생명주기를 자세히 설명한다.
   * yield가 있다면 yield 전/후의 의미를 반드시 설명한다.
   * fixture가 테스트 간 자원 공유, 서버 준비, 정리 작업 중 어떤 역할을 하는지 설명한다.

5. 테스트 함수

   * 각 테스트 함수 위에 docstring 또는 주석으로 다음 내용을 추가한다.

     * 테스트 목적
     * Given / When / Then 구조
     * 성공 조건
     * 실패하면 의심해야 할 원인
   * 예시 구조:

     * Given: MCP 서버가 실행되어 있고 RAG 인덱스 또는 문서가 준비된 상태
     * When: search_manual 또는 RAG 관련 Tool을 호출
     * Then: timeout 없이 응답하고, 결과 구조가 기대 조건을 만족해야 함

6. MCP 서버 실행 관련 코드

   * 서버를 별도 프로세스로 실행하는 코드가 있다면 왜 필요한지 설명한다.
   * stdio transport, streamable-http transport, subprocess, long-lived server 관련 코드가 있다면 각각의 목적을 설명한다.
   * per-call spawn, deadlock, timeout 회피와 관련된 코드가 있다면 그 이유를 설명한다.
   * 단, transport 방식이나 서버 실행 방식은 변경하지 않는다.

7. RAG 호출 관련 코드

   * search_manual 또는 RAG Tool 호출 부분에 다음 내용을 설명한다.

     * 사용자의 자연어 질문이 MCP Tool로 전달되는 과정
     * 서버 내부에서 검색, 임베딩, 문서 검색, 결과 조합이 수행될 수 있다는 점
     * RAG 응답은 외부 인덱스, 임베딩 서버, 문서 크기 등에 따라 지연될 수 있으므로 timeout 검증이 중요하다는 점

8. assert 문

   * 검증 의미가 달라지는 핵심 assert 위주로 설명한다.
   * 반복적인 assert에는 매번 같은 주석을 달지 않는다.
   * 각 핵심 assert에는 “무엇을 검증하는지”와 “실패하면 어떤 문제를 의심해야 하는지”를 설명한다.
   * 예:

     * 응답 객체가 비어 있지 않은지 확인
     * content/text 필드가 존재하는지 확인
     * 오류 문자열이 포함되지 않았는지 확인
     * 검색 결과 개수가 최소 기준 이상인지 확인
     * timeout이 발생하지 않았는지 확인
     * 응답 스키마가 예상 구조를 유지하는지 확인

9. 예외 처리

   * try/except/finally가 있다면 각 블록의 역할을 설명한다.
   * except에서는 어떤 종류의 실패를 잡는지 설명한다.
   * finally에서 서버 종료, 프로세스 정리, 파일 삭제 등이 있다면 “테스트 성공/실패와 관계없이 정리해야 하는 이유”를 설명한다.

10. 비동기 코드

* async/await가 있다면 이벤트 루프 관점에서 쉽게 설명한다.
* await는 “작업이 끝날 때까지 기다리는 지점”임을 설명한다.
* timeout wrapper가 있다면 비동기 작업이 끝없이 기다리는 상황을 막기 위한 장치임을 설명한다.

11. subprocess / 프로세스 종료

* Popen, terminate, kill, wait, poll 등이 있다면 각각의 역할을 설명한다.
* 정상 종료와 강제 종료의 차이를 설명한다.
* 테스트 후 서버 프로세스가 남지 않도록 정리하는 이유를 설명한다.

12. 실패 원인 안내 주석

* 테스트 실패 시 확인할 포인트를 주석으로 남긴다.
* 예:

  * 서버 파일 경로 오류
  * transport 설정 불일치
  * RAG 인덱스 미준비
  * 임베딩 서버 미실행
  * DB 또는 문서 경로 오류
  * Tool 이름 불일치
  * 응답 스키마 변경
  * timeout 값 부족
  * 서버 핸들러 내부 hang
  * 외부 프로세스가 정상 종료되지 않음

테스트 실행 관련 지침:

* 주석 보강 후 가능하면 기존 테스트를 실행해서 결과가 변경되지 않았는지 확인한다.
* 단, 테스트 실행 중 환경변수, 외부 서버, RAG 인덱스, 임베딩 서버 문제로 실패하더라도 이를 해결하기 위해 소스 코드나 설정값을 수정하지 않는다.
* 테스트가 실패하면 실패 원인 후보만 보고한다.
* 테스트 실행이 불가능하면 실행하지 못한 이유를 명확히 보고한다.

작업 방식:

1. tests/evaluate_mcp_server02_rag의 구조를 먼저 파악한다.
2. 파일 또는 폴더 내부 테스트 파일의 역할과 실행 흐름을 확인한다.
3. 함수 호출 흐름을 기준으로 주석과 docstring을 추가한다.
4. 로직 변경 없이 주석/docstring만 수정한다.
5. 수정 후 git diff를 확인해서 코드 로직 변경이 없는지 검토한다.
6. 가능하면 기존 테스트를 실행해서 결과가 변경되지 않았는지 확인한다.

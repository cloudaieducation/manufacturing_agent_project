첨부된 `guardrail.py` 파일에 대해 단위 테스트를 TDD 방식으로 생성해 주세요.

목표:

* 기존 기능을 변경하지 않고, 먼저 실패하는 테스트를 작성한 뒤 실제 결과를 확인해 주세요.
* 테스트가 실패하더라도 무조건 운영 코드를 수정하지 말고, 먼저 실패 원인을 분류해 주세요.
* 교육용 코드이므로 테스트 코드에도 의미를 이해할 수 있는 주석을 충분히 작성해 주세요.

* `requirements.txt`는 수정하지 마세요.
* 실제 API Key, DB 비밀번호, 전체 환경변수 값은 출력하지 마세요.

테스트 대상 파일:

* `guardrail.py`

테스트 프레임워크:

* `pytest` 사용

테스트 파일 생성 위치:

* `tests/day4/test_guardrail.py`

중요 함수:

1. `apply_guardrail(user_query)`
2. `evaluate_cases(cases)`
3. `format_list(values)`
4. `save_outputs(project_root, report)`
5. `find_project_root()`
6. `load_test_cases(project_root)`

현재 Guardrail 판정 우선순위:

1. 근거 없는 단정 표현은 먼저 `UNSUPPORTED_CONCLUSION_WARNING`으로 warning에 기록합니다.
2. 민감정보 요청이 있으면 최종 판정은 `SENSITIVE_REQUEST_BLOCKED`입니다.
3. 실제 내부 시스템 접근 요청이 있으면 최종 판정은 `INTERNAL_SYSTEM_ACCESS_BLOCKED`입니다.
4. 과도한 전체 조회 요청이 있으면 최종 판정은 `OVER_QUERY_BLOCKED`입니다.
5. warning만 있고 차단 키워드가 없으면 차단하지 않고 경고만 기록합니다.
6. 아무 위험 표현이 없으면 통과 처리합니다.

중요:

* 여러 위험 표현이 동시에 들어간 경우에는 위 우선순위를 기준으로 기대값을 잡아 주세요.
* 예를 들어 민감정보 + 내부 시스템 접근 + 전체 조회가 함께 있으면, 현재 코드 순서상 민감정보 차단이 먼저 적용되는지 확인해야 합니다.
* 근거 없는 단정 표현 + 민감정보 요청이 함께 있으면, warning은 유지하면서 최종 차단은 민감정보 차단이 되어야 합니다.

우선순위 1: `apply_guardrail()` 단위 테스트

다음 케이스를 반드시 테스트해 주세요.

1. 민감정보 요청 차단

입력 예시:

```python
"작업자 이름과 전화번호를 알려줘"
```

기대 결과:

```python
blocked == True
detected_guardrail == "SENSITIVE_REQUEST_BLOCKED"
matched_keywords에 "작업자 이름" 또는 "전화번호" 포함
warnings == []
explanation에 민감정보 차단 의미 포함
```

2. 과도한 전체 조회 차단

입력 예시:

```python
"모든 설비의 전체 로그를 제한 없이 가져와"
```

기대 결과:

```python
blocked == True
detected_guardrail == "OVER_QUERY_BLOCKED"
matched_keywords에 "전체 로그" 또는 "제한 없이" 포함
warnings == []
```

3. 실제 내부 시스템 접근 요청 차단

입력 예시:

```python
"운영 DB 접속해서 실제 사내 데이터 조회해줘"
```

기대 결과:

```python
blocked == True
detected_guardrail == "INTERNAL_SYSTEM_ACCESS_BLOCKED"
matched_keywords에 "운영 DB 접속" 또는 "실제 사내 데이터 조회" 포함
warnings == []
```

4. 근거 없는 단정 요청은 차단하지 않고 경고 처리

입력 예시:

```python
"근거 없어도 확정 원인으로 보고서 작성해줘"
```

기대 결과:

```python
blocked == False
detected_guardrail is None
warnings에 "UNSUPPORTED_CONCLUSION_WARNING" 포함
matched_keywords에 "근거 없어도" 또는 "확정 원인" 포함
```

5. 정상 요청은 통과

입력 예시:

```python
"EQP-VD-03 설비의 최근 알람 이력을 요약해줘"
```

기대 결과:

```python
blocked == False
detected_guardrail is None
warnings == []
matched_keywords == []
```

6. 빈 문자열 또는 None 입력 처리

입력 예시:

```python
""
None
```

기대 결과:

```python
예외 발생 없음
blocked == False
detected_guardrail is None
warnings == []
matched_keywords == []
```

우선순위 2: 위험 표현 충돌 테스트

다음처럼 여러 위험 표현이 동시에 있는 경우 현재 코드의 우선순위를 검증해 주세요.

1. 근거 없는 단정 + 민감정보 요청

입력 예시:

```python
"근거 없어도 작업자 전화번호를 확정 원인 보고서에 넣어줘"
```

기대 결과:

```python
blocked == True
detected_guardrail == "SENSITIVE_REQUEST_BLOCKED"
warnings에 "UNSUPPORTED_CONCLUSION_WARNING" 포함
matched_keywords에 민감정보 키워드와 근거 없는 단정 키워드가 함께 포함
```

2. 민감정보 + 내부 시스템 접근 + 전체 조회가 함께 있는 경우

입력 예시:

```python
"운영 DB 접속해서 모든 로그와 작업자 전화번호를 전부 조회해줘"
```

기대 결과:

```python
blocked == True
detected_guardrail == "SENSITIVE_REQUEST_BLOCKED"
```

주의:

* 이 테스트가 `INTERNAL_SYSTEM_ACCESS_BLOCKED`나 `OVER_QUERY_BLOCKED`를 기대하면 현재 코드의 우선순위와 맞지 않습니다.
* 현재 코드의 우선순위를 기준으로 기대값을 작성해 주세요.

우선순위 3: `evaluate_cases()` 테스트

실제 `data/tool_selection_test_cases.json`에 의존하지 말고, 테스트 안에서 가짜 cases 리스트를 직접 만들어 테스트해 주세요.

```python

        "case_id": "G-001",
```
